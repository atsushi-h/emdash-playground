# ミナトテック お知らせPoC（フェーズ1）

架空の株式会社ミナトテック（精密部品加工・機械設計、約35名）のお知らせ運用を検証するPoCです。企業サイト全体のデザインは後続フェーズです。

## ローカルで開く

```sh
bun dev --host 127.0.0.1 --port 4322
```

- 一覧：<http://127.0.0.1:4322/news/>
- 初期記事：<http://127.0.0.1:4322/news/welcome/>
- 管理画面：<http://127.0.0.1:4322/_emdash/admin/content/posts>

今回4321番は別プロジェクトが使用していたため、4322番で確認しました。通常の`bun dev`は4321番です。

このローカル環境ではEmDash標準の開発用セットアップで作成した`dev@emdash.local`を使って検証しました。開発中のみ、標準の`/_emdash/api/auth/dev-bypass?redirect=/_emdash/admin/content/posts`からログインできます。このエンドポイントはEmDash自身が本番では無効にします。

## 実装内容

- コレクションの内部名は`posts`を維持。管理画面の表示名は「お知らせ」。項目は「タイトル」「メイン画像」「本文」「概要」。
- 一覧は公開日の降順、20件ずつのカーソル方式。日本語の日付は`ja-JP`・`Asia/Tokyo`。
- 詳細は標準の`getEmDashEntry`、`Image`、`PortableText`、`getSeoMeta`、`EmDashHead`を使用。
- 公開URLは`/news/`と`/news/{slug}/`。スラッシュなしと旧`/posts`は308で転送し、クエリを保持。管理画面/APIを巻き込まないようグローバルな`trailingSlash`は変更していません。
- プレビューはEmDashの署名検証を使用。確認用の表示と`noindex, nofollow`を設定。標準ミドルウェアがプレビューの共有キャッシュを回避し、応答は`private, no-store`。
- 未存在・一般閲覧の未公開記事は404。お知らせクエリの失敗は503、日本語案内・`no-store`。正常な空一覧は200。
- コンテンツ・設定・メニューのキャッシュ依存を登録。ルートキャッシュ自体は新たに有効化していません。
- ホーム、カテゴリ、タグ、検索・サイトマップから新URLへ接続。`src/live.config.ts`は変更していません。

## 既存DBへの適用

**seedの変更をデプロイしても、既存DBの設定は更新されません。** seedは新規環境の初期構築用です。

対象DBとメディアをバックアップし、既存スラッグ・公開状態・記事ID・履歴を保持したまま、次を管理画面で適用します。

1. Content Typesで既存`posts`を編集。表示名と単数表示名を「お知らせ」、URLパターンを`/news/{slug}/`にする。内部名・フィールドの内部名・型・supportsは維持する。
2. 既存フィールドの表示名だけを上記の日本語に変更する。
3. サイト設定でタイトルを「株式会社ミナトテック」、説明を「精密部品加工・機械設計を通じて、ものづくりを支えます。」、タイムゾーンを`Asia/Tokyo`にする。
4. `primary`メニューの既存項目を「ホーム」→`/`、「お知らせ」→`/news/`、「会社概要」→`/about/`に変更する。他の既存項目は用途を確認して残す。
5. 新しいルートが動くコードとDBのURL設定を、検証環境で揃える。設定変更前に既存の`news`固定ページやURL上書き、プレビューの環境変数がないか確認する。
6. 開発サーバーから生成される`emdash-env.d.ts`を確認する。リモートDBの場合は公式CLIの`emdash types --url ...`で確認する。生成ファイルを手編集しない。

今回はバックアップ後、この**ローカルDBのみ**に標準のEmDashスキーマ・設定・メニューAPIで適用しました。Cloudflare上のDBには接続していません。既存のWelcome記事とAboutページの内容は上書きしていません。新規環境用seedには日本語の初期記事・会社概要を用意しています。

### バックアップと戻し方

変更前のローカルD1/R2等は`.wrangler/backups/20261031-093227/`に保存しました。D1本体に未反映WALがなく、このプロジェクトのサーバー未起動の状態で取得しています。バックアップや開発用セッションをGitへ追加しないでください。

通常の取り消しは管理画面で元のラベル・URL・サイト設定・メニューへ戻し、対応するコードも戻します。全データを戻す必要がある場合は、このプロジェクトのサーバーを停止して現在の状態も別途退避し、バックアップから`.wrangler/state`を復元します。稼働中のDBファイルを置き換えないでください。

### 管理画面での最終確認

1. 上記の開発用ログインから「お知らせ」を開く。既存の検証記事または新しい検証用記事でタイトル・概要・本文・画像を入力し、下書き保存する。
2. View on siteでプレビューを開く。新しい`/news/`経路とプレビュー表示を確認する。プレビューURLは所持者が閲覧できるため、共有範囲を限定する。
3. 別の未ログインブラウザーで、下書きが一覧・詳細・検索に出ないことを確認する。
4. 公開し、一般表示へ反映されることを確認する。
5. 本文を変更して下書き保存する。プレビューだけが新しい内容になり、通常表示は公開済みの内容を保つことを確認する。
6. 再公開後、通常表示が更新されることを確認する。
7. 非公開化し、一覧から消え、詳細が404になることを確認する。各操作の間にビルドや再起動を行わない。

## Workersでの後続確認

検証用Cloudflareアカウント、D1/R2の接続先、デプロイ権限、検証URLとログイン手段を確定してから実施します。本番データを使う場合は先にバックアップします。

- `DB`/`MEDIA`、アダプターが追加するセッション等のバインディング、サイト公開オリジン、Cron設定を確認。
- 検証環境へコードをデプロイ。既存DBには上記設定を別途適用し、初期seedの再適用やDB初期化をしない。
- 管理画面のURL、プレビュー、画像、SEOのオリジンが検証ドメインと一致することを確認。
- 同じ公開フローを繰り返し、再デプロイなしで反映されることを確認。キャッシュを使う構成では更新・非公開化の無効化と、プレビュー後も一般閲覧に下書きが混入しないことを確認。
- 予約公開・Cronの実行確認は、通常の公開フローとは別に記録する。
